\subsection{Work plan}\label{sec:workplan}
\secinfo{Grégoire Mariette}{Jimena Narvaez del Cid}

The work is organised in six task groups that follow the phases of the project (T1--T6), a management task group (T7) and one stretch goal (T8). Each task has one lead, who is accountable for its result, a list of participants, a duration in weeks and a measurable indicator of completion. Every team member leads at least two tasks. For each task we give the objectives it serves (O1--O5, Section~1.2) and the risks it mitigates (RK1--RK5, Section~3.5). Team members are referred to by first name: Abdul Moiz, Grégoire, Jimena, Joris, Louis Nathan, Mikle and Vlad.

\taskgroup{T1 Toolchain and infrastructure}{Grégoire}{W1--W5}
\task{T1.1}{Reproducible HEIR environment}{Grégoire}{Joris}{W1--W3}{Pin one HEIR release and package it with all dependencies in a Docker image that runs on our laptops and on the DACS GPU cluster. \textit{Indicator:} all seven members and the cluster build the image and run HEIR's bundled examples. \textit{Serves} O5; \textit{mitigates} RK1.}
\task{T1.2}{End-to-end CPU sanity check}{Abdul Moiz}{Grégoire}{W3--W4}{Compile a single encrypted 8-bit comparison with HEIR's CGGI (Boolean) pipeline, run it on a CPU backend and decrypt the result. \textit{Indicator:} correct output on 100 random input pairs; compile and run time recorded. \textit{Serves} O1; \textit{mitigates} RK2, RK5.}
\task{T1.3}{Accelerator access}{Mikle}{Vlad}{W1--W5}{Reserve GPU nodes on the DACS cluster, apply for TPU access (Google TPU Research Cloud or free cloud-notebook TPUs) and track the status of HEIR's GPU backend. \textit{Indicator:} written access status per hardware type, used for the decision at MS2. \textit{Serves} O3; \textit{mitigates} RK4.}

\taskgroup{T2 Algorithms and correctness}{Abdul Moiz}{W3--W7}
\task{T2.1}{Oblivious sorting networks}{Abdul Moiz}{Louis Nathan}{W3--W7}{Implement bitonic sort and odd-even merge sort, whose sequence of comparisons does not depend on the data, parameterised by list length $N$ and bit width $b$; start at $N=4$, $b=8$. \textit{Indicator:} both networks compile and run for $N \in \{4, 8, 16\}$, $b=8$. \textit{Serves} O1, O2; \textit{mitigates} RK2.}
\task{T2.2}{Oblivious shuffle}{Mikle}{Jimena}{W4--W7}{Implement shuffling as sorting by encrypted random keys, reusing T2.1. Agree with Roseman Labs on where the randomness comes from (client-supplied encrypted keys or encrypted pseudo-random generation) and what the server may learn. \textit{Indicator:} documented threat model; shuffle compiles and runs for $N \in \{4, 8, 16\}$, $b=8$. \textit{Serves} O1.}
\task{T2.3}{Plaintext reference and test suite}{Vlad}{Joris}{W3--W6}{Python reference implementations and an automated test suite that runs after every change. \textit{Indicator:} sort output equals the plaintext sort on $\geq 100$ random inputs per configuration; shuffle output is a permutation of its input, and for $N=4$ the 24 possible permutations pass a $\chi^2$ uniformity test over $\geq 240$ runs. \textit{Serves} O1; \textit{mitigates} RK5.}

\taskgroup{T3 Scalability and limits}{Joris}{W6--W9}
\task{T3.1}{Benchmark harness}{Joris}{Grégoire}{W6--W8}{Scripted runner, submitted as cluster batch jobs, that records compile time, run time, throughput, peak memory of compilation and of execution separately, and ciphertext and key sizes. Each configuration is repeated at least five times; we report median and interquartile range and store all raw data in the repository. \textit{Indicator:} any measurement can be reproduced with one command. \textit{Serves} O2, O5; \textit{mitigates} RK3.}
\task{T3.2}{CPU parameter sweep}{Joris}{Abdul Moiz, Louis Nathan}{W8--W9, unattended runs may continue in W10}{Double $N$ from 4 upwards for $b \in \{8, 16, 32\}$ until a run exceeds the per-run budget (provisionally 1\,h and 64\,GB RAM, fixed at MS1 from the cluster's capacity). \textit{Indicator:} maximum $N$ per $b$ for sort and shuffle, with the limiting factor (time, compile memory or run memory). \textit{Serves} O2; \textit{mitigates} RK3.}

\taskgroup{T4 Cross-hardware execution}{Mikle}{W6--W14}
\task{T4.1}{GPU execution}{Grégoire}{Mikle}{W8--W10, W13--W14}{Repeat the T3.2 grid on the DACS GPU nodes with HEIR's GPU backend if MS2 confirms it is usable; otherwise run the hand-written TFHE-rs baseline (T4.3) on GPU as fallback. \textit{Indicator:} run time, memory and throughput for the same $(N, b)$ grid as on CPU. \textit{Serves} O3; \textit{mitigates} RK4.}
\task{T4.2}{TPU execution}{Vlad}{Abdul Moiz}{W8--W10, W13--W14}{Compile the CGGI programs for TPU through HEIR's Jaxite backend if TPU access is confirmed at MS2. \textit{Indicator:} as for T4.1; without TPU access, a documented limitation instead of results. \textit{Serves} O3; \textit{mitigates} RK4.}
\task{T4.3}{Hand-written baseline}{Mikle}{Vlad}{W6--W9}{Implement the same sorting network directly in TFHE-rs to measure the overhead of HEIR-generated code against hand-written code on identical hardware. \textit{Indicator:} run-time ratio HEIR\,/\,hand-written per $(N, b)$. \textit{Serves} O3.}

\taskgroup{T5 Cloud cost model}{Jimena}{W8--W14}
\task{T5.1}{Pricing data and hardware mapping}{Jimena}{Louis Nathan}{W8--W9}{Collect on-demand prices of comparable CPU, GPU and TPU instances from at least two cloud providers on one fixed date, and map each cluster node to its closest instance type. \textit{Serves} O4.}
\task{T5.2}{Cost per operation}{Jimena}{Grégoire}{W13--W14}{Combine measured run times and memory needs with the T5.1 prices into the cost per sort and per shuffle for each $(N, b)$ and hardware type, and identify the cheapest configuration per input size. \textit{Indicator:} cost table with all assumptions stated. \textit{Serves} O4.}

\taskgroup{T6 Analysis, reporting and handover}{Louis Nathan}{W13--W16}
\task{T6.1}{Results analysis}{Louis Nathan}{all}{W13--W14}{Answer the research questions and compare the results with related work.}
\task{T6.2}{Final report (D2)}{Louis Nathan}{all}{W13--W16}{}
\task{T6.3}{Final presentation and demonstration (D3)}{Abdul Moiz}{all}{W15--W16}{}
\task{T6.4}{Repository handover (D6)}{Joris}{Grégoire}{W15--W16}{README, Docker image, scripts and raw data handed over to Roseman Labs. \textit{Serves} O5.}

\taskgroup{T7 Project management and customer liaison}{Vlad}{W1--W16}
\task{T7.1}{Team coordination}{Vlad}{all}{W1--W16}{Weekly team meeting and task board; progress is checked against the milestones, and a missed milestone triggers re-planning in the next meeting.}
\task{T7.2}{Customer and supervisor contact}{Jimena}{Louis Nathan}{W1--W16}{Meeting with Roseman Labs every two weeks (to be confirmed); agreement on deliverables, confidentiality and the shuffle threat model (T2.2); interim update D4 at MS4.}

\taskgroup{T8 Stretch goal: FHE compared with MPC}{Louis Nathan}{W13--W15}
\task{T8}{FHE vs.\ MPC for sorting and shuffling}{Louis Nathan}{Joris}{W13--W15}{Started only if MS4 is reached on time and Roseman Labs agrees. Compare our sort and shuffle results with MPC figures provided by Roseman Labs or taken from the literature, following the system-level comparison of \cite{huang2026beyond}. Reported as an additional section in D2; not needed for O1--O5.}

\paragraph{Contingency.} Objectives O1 and O2 depend only on CPU results, which are complete at MS4 (W9). The accelerator runs (T4.1, T4.2) have four working weeks plus unattended runs in W10, and can be reduced to fewer configurations without affecting O1 and O2. W10 is the buffer for delayed CPU runs, and the stretch goal T8 is the first activity dropped if the schedule slips.

\subsection{Risk management}                            % 3 pages max
\secinfo{Abdul Moiz Akbar}{}
\medskip
This project relies on a research-grade compiler, computationally expensive
cryptographic workloads, and hardware we do not fully control. Risks are rated
by probability of occurrence and impact on the project (L = low, M = medium,
H = high). Where a risk concerns the limits of HEIR itself, reaching that limit is recorded as an experimental result rather than a project failure.
